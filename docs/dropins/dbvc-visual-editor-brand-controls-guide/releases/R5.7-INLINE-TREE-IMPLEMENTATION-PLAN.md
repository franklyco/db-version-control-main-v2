# R5.7 — Inline Tree (Option C-1) implementation plan

**Drafted:** 2026-09-01.
**Status:** Planning only. Nothing below is authorized to execute yet.
**Provenance:** Shape chosen from the four-option design review
(`R5-REMAINING-UNLOCK-FRONTIERS.md` §R5.7 + the accompanying lo-fi
artifact). Product / UX-recommended pick. Drag reorder deferred to a
follow-up sub-slice (R5.7-C-2), not in scope here.

**Scope statement:** Teach the Brand Control Center drawer to render
repeater / flexible-content fields as expandable tree rows — each
repeater is one drawer entry until touched; expanding reveals its rows;
expanding a row reveals its curated subfields; each leaf keeps the
existing Open contract (mints a normal single-subfield descriptor into
the existing editor panel). Zero changes to the panel-side controllers,
zero new REST routes for the UI-shape decision itself (one small
descriptor addition is the entire backend contract change), and zero
new mutation authority. Drag-reorder is explicitly R5.7-C-2, not R5.7-C-1.

**Live-site unlock at completion:** 1 curated Vertical record
(`settings_nav_menus>menus>menu_posts` if `menus` turns out to be a
repeater — the pre-slice assumption). Coverage moves from 397 to 398 of
400 curated records (99.5%). More importantly, the descriptor + save
infrastructure this slice ships is reusable for every future
repeater-nested curation record without further backend work.

---

## Shape summary — what C-1 IS

The drawer becomes a shallow tree. The R4-C-2 collapsible group-header
pattern (already shipping) is one level; C-1 adds two more:

```
▾ [Category tab active]
  ▾ [Group header — R4-C-2 established]
    Regular scalar row                          [Open]
    Regular reference-collection row            [Open]
    ▸ Repeater parent row              [3 rows]        ← NEW: level 1 tree
    ...
```

Expanded:

```
▾ [Group header]
    ▾ Repeater parent row              [3 rows]        ← level 1 open
      ▸ Row 1 label                                    ← NEW: level 2
      ▾ Row 2 label                                    ← level 2 open
        Menu title           [text]              [Open]  ← NEW: level 3 leaf
        Menu posts           [relationship]      [Open]
        Show in footer       [true/false]        [Open]
      ▸ Row 3 label
```

Design invariants:
- **Only leaves have Open buttons.** Parents (repeater and row) render
  a disclosure triangle + a row-count chip; they do NOT open the panel.
- **The panel contract is byte-identical to R5.4.** A leaf's `Open`
  mints a single-subfield descriptor and mounts the existing editor
  panel exactly the way any R5.1..R5.4 record does today.
- **Server-side stays flat.** The list endpoint returns records with an
  optional `parentPublicId` field; ancestor-flattening happens
  client-side. Filter/search server contract does not learn about the
  tree.
- **No new REST route.** The batch value-summary endpoint (R4-C-1b) is
  called for visible leaves inside expanded parents. Parents render
  no chip.

## Slice split (three checkpoints)

C-1 is too big to land as a single slice. The split mirrors R5.1's
a/b/c and keeps each checkpoint independently shippable:

| Slice | Layer | Estimated size | Ship state at checkpoint |
|---|---|---|---|
| **R5.7-a** | DBVC backend + Vertical unroll | ~R5.6-comparable | Drawer surfaces N × M records for each curated repeater; renders them **flat** (Option-A-like interim). Save works with row-signature integrity guard. |
| **R5.7-b** | Drawer tree UI | ~R4-C-2 comparable | Drawer surfaces one parent record per repeater; expand reveals rows; expand a row reveals leaves. Save-status-strip fires normally. |
| **R5.7-c** | Real-browser QA + release notes | Docs slice | Real-browser QA at both desktop viewports; QA report; release-notes/rollback update; tracker close. |

Rationale for this split:

1. **R5.7-a is fully shippable on its own.** The interim flat state is
   the same as Option A — it correctly unlocks the record with a
   working save path. If R5.7-b never lands, the record still works.
2. **R5.7-b is a pure client-side upgrade.** It doesn't change the
   backend contract or the save path — every server-side test from
   R5.7-a keeps passing byte-identically. This is the safest way to
   ship a substantial UI change.
3. **R5.7-c is the residual gate** (mirrors R3-D and R2-E4's release
   notes shape).

## Prerequisites and blocking spike

### Q2 row-identity spike

**Before R5.7-a can write code**, run a ~30–60 min investigation:

- Load ACF locally, create a repeater with a couple of rows, save.
- In a test rig, call `get_field($repeater_name, 'option', false)` and
  inspect the returned array shape.
- Verify whether individual rows carry a stable ACF-assigned key
  (something like `acf_row_XXXX`) that survives reorders.
- If yes → the descriptor's `source.row_key` is the primary identifier
  and `row_index` becomes a display-only positional hint.
- If no → `row_index` is the identifier and `expected_row_signature`
  becomes mandatory to guard against stale writes.

The spike **cannot be skipped** — its outcome decides one line of the
`AbstractAcfResolver::writeRepeaterSubfieldValue` implementation.

Record the outcome in a short evidence-log row (E-114 or equivalent)
before starting R5.7-a. If the spike shows row keys ARE stable, the
signature guard is still useful as defense-in-depth but not
load-bearing; document that in the resolver's docblock.

### Curation JSON `display_subfield` hint

Decide upfront whether the maintainer needs to control which subfield
of a row becomes the row's display label. Two paths:

- **Configured**: curation JSON gains an optional `display_subfield`
  string per curated repeater. The Vertical provider reads it when
  labeling rows.
- **Heuristic**: the Vertical provider picks the first non-empty
  text-family subfield value of each row. No JSON change.

MVP recommendation: **heuristic first**, with the `display_subfield`
hint added only if the heuristic produces a bad label on the live-site
`menus` record. Cheaper and doesn't touch the R3-BX curation admin.

## R5.7-a — DBVC backend + Vertical unroll

### Goal

Ship a working save path for repeater-subfield writes with row-identity
integrity. Vertical provider unrolls each curated repeater into N × M
`ControlRecord`s so the drawer surfaces them (flat, as a temporary
Option-A-like state until R5.7-b lands).

### Implementation steps (in order)

1. **Land the Q2 spike outcome as a short evidence-log row.** Document
   which strategy the resolver will use.

2. **New descriptor shape in
   [`SharedGlobalsDescriptorFactory.php`](../../../addons/visual-editor/src/Registry/Providers/SharedGlobalsDescriptorFactory.php)** —
   add a `buildRepeaterSubfieldDescriptor()` private helper. Emits:
   ```
   source:
     type: "acf_repeater_subfield"
     container_type: "repeater"
     parent_field_name: "menus"
     parent_field_key: "field_menus"
     row_index: 2                       # 0-indexed positional
     row_key: "row_5f42b1"              # ACF stable key OR null
     expected_row_signature: "a3f4c1..."# sha1 of row values at mint time
     field_name: "menu_posts"           # leaf
     field_key: "field_menu_posts"
     field_type: "relationship"
     ...normal leaf source metadata...
   mutation:
     contract: "shared_field"           # inherited; same whitelist
     kind: "scalar" | "reference_collection"
   ```
   Contract type stays `shared_field` — no new mutation contract to
   whitelist. `buildSharedFieldDescriptor()` config-bag pattern
   extends: `{resolver: <family-appropriate>, input: <family-appropriate>,
   source_context: "toolbar_shared_global_option_repeater_subfield", ...}`.

3. **Extend
   [`AbstractAcfResolver.php`](../../../addons/visual-editor/src/Resolvers/AbstractAcfResolver.php)**
   with a `writeRepeaterSubfieldValue($source, $value)` helper (if
   the current `isRepeaterSubfieldSource()` helper's write path doesn't
   already handle this shape). The write path:
   1. Lift parent's current rows via `get_field($parent_field_name, 'option', false)`.
   2. Resolve target row: by `row_key` if present, else by
      `row_index`. If lookup fails → throw
      `RepeaterRowLookupFailed`.
   3. Verify `expected_row_signature` against a freshly-computed
      signature of the resolved row. On mismatch, throw
      `ConcurrentReorderDetected` (a specific, structured error the
      panel can surface — see save-status-strip note below).
   4. Update the target row's subfield value.
   5. Write the whole rows array back via
      `update_field($parent_field_key, $new_rows, 'option')` — the same
      RK-013 "write THROUGH the parent" pattern R2-F pioneered.
   6. Emit a resolver-level event `dbvc_visual_editor_repeater_subfield_saved`
      carrying `{parent_field_name, row_index, subfield_name}` so
      downstream cache invalidation can subscribe.

4. **New public static
   `SharedGlobalsControlProvider::buildRepeaterRowSignature($row_data)`** —
   deterministic sha1 of the row's serialized field-value map. Excludes
   any auto-generated key ACF might add (e.g., `acf_row_*`). Used by
   the descriptor factory AND the resolver so both sides compute the
   same hash.

5. **Vertical provider `getControls()` extension** in
   [`class-vf-vertical-control-provider.php`](../../../../themes/vertical/functions/features/dbvc-visual-editor/includes/class-vf-vertical-control-provider.php).
   Detect curated records whose `field_name` matches a
   `parent>[]>child` repeater-subfield pattern (informed by
   `parentChainIsGroupOnly` returning false + a new
   `parentChainRepeaterInfo` helper that reports "there's a repeater at
   depth D with parent field X"). For each such record:
   1. Lift the parent repeater's rows via
      `get_field($parent_field_name, 'option', false)`.
   2. For each row, emit ONE synthetic `ControlRecord` with:
      - `publicId = "vertical:{curation_id}::row_{row_index_or_key}"`
        (deterministic; survives reload)
      - `label = "{curated_label} · {row_display_label}"` where
        row_display_label comes from the `display_subfield` hint or
        heuristic
      - `group_title = curated_group_title`
      - `category = curated_category`
      - `priority = curated_priority`
      - `status = "available"` (unlocked; the ancestry gate R5.6
        installed still applies, but repeater-nested passes it
        because we're routing through the new descriptor path)
      - `fieldFamily = leaf_family`
      - `source = {..., row_index, row_key, subfield_name,
        subfield_key, expected_row_signature, parent_field_name,
        parent_field_key}`
      - `parentPublicId = "vertical:{curation_id}::repeater"` — **safe to
        emit now**, the current drawer ignores it (R5.7-b consumes it)
   3. Also emit ONE `parentPublicId=null` synthetic parent
      `ControlRecord` per repeater:
      - `publicId = "vertical:{curation_id}::repeater"`
      - `label = curated_label`
      - `status = "unsupported"` (the parent itself has no editable
        contract — its children do; today's drawer will not render
        an Open button on it; tomorrow's R5.7-b renders the disclosure
        triangle instead)
      - New optional `meta.childCount = N` so R5.7-b's parent row can
        render `[N rows]` without a re-fetch
      - New optional `meta.role = "repeater_parent"` — a stable
        marker so the drawer can distinguish tree parents from
        `status='unsupported'` records that are truly unsupported
6. **Vertical `buildDescriptor()`** — recognize repeater-subfield
   publicIds (`::row_N` in the local id), extract the row_index/key,
   look up the parent field via `acf_get_field`, delegate to DBVC's
   `SharedGlobalsDescriptorFactory::buildRepeaterSubfieldDescriptor()`.
   Return null for parent publicIds (they have no descriptor by design).
7. **Vertical `buildValueSummary()`** — for repeater-subfield leaves,
   lift the specific row, resolve the subfield value, delegate to the
   appropriate family's public static `build*Summary` builder. Return
   null for parents.
8. **Extend `SharedGlobalsControlProvider::supportedFieldTypes()`?**
   No new field types — this slice widens the recognized SOURCE shape,
   not the field-type whitelist. Every family already supported
   (text/textarea/url/email/number/select/checkbox/radio/button_group/link/wysiwyg/true_false/image/color_picker/relationship/post_object)
   works uniformly at the repeater leaf.

## R5.7-b — Drawer tree UI

### Goal

Fold the flat R5.7-a records into a tree render — parent (repeater) at
level 1, row at level 2, leaf subfield at level 3. Reuse the R4-C-2
collapsible-group vocabulary; the tree is a two-deep extension of the
same idea.

### Implementation steps (in order)

1. **[`ControlRecord.php`](../../../addons/visual-editor/src/Registry/ControlRecord.php) additions:**
   - New optional field `parentPublicId: ?string` in the value object.
   - `fromArray()` accepts + validates (must be a string starting with
     `<provider>:` matching the same provider prefix as the record's
     own publicId; else drop the field with an observable
     `dbvc_visual_editor_control_registry_invalid` fire, don't reject
     the record).
   - `toArray()` / `toSafeArray()` include the field. **This is safe
     for the wire** — a publicId is opaque to the client and never
     identifies a target; the safe projection contract stays
     honored.
   - New optional `meta.role: ?string` (`"repeater_parent"` for R5.7,
     designed for arbitrary future roles — think `"flexible_layout_parent"`,
     etc.). Whitelist-normalized like `status`.
   - New optional `meta.childCount: ?int`.

2. **[`ControlRegistry.php`](../../../addons/visual-editor/src/Registry/ControlRegistry.php)
   deterministic sort update:** child records sort AFTER their parent
   in the response. New tiebreak — a record with `parentPublicId=X`
   sorts immediately after the record whose `publicId=X`, in the order
   the provider emitted them.

3. **`brand-control-center-app.js` state additions:**
   - `state.expandedRows: Set<publicId>` — persisted to
     `localStorage['dbvc.ve.control-center.expanded-rows']`. Records
     only viewer DEVIATIONS from the "collapsed by default" rule
     (same pattern R4-C-2 uses for groups). Try/catch-wrapped for
     private-window safety.
   - `state.searchAutoExpanded: Set<publicId>` — transient; populated
     while a search query is active; cleared on search clear.

4. **`renderList()` extension:**
   - Group child records under their parent (records with
     `parentPublicId=X` are visually nested under record `publicId=X`).
   - Parent rows render:
     - Disclosure triangle (`▸` / `▾`) toggled by `is-expanded` class
     - Row label + descriptor line (as today)
     - Right-side count chip `[N items]` (from `meta.childCount`,
       fallback to counted children)
     - **No Open button**
     - ARIA: `role="treeitem"` `aria-expanded="true|false"`
       `aria-level="1"`
   - Child rows render:
     - Nested indentation via new `.__row.is-level-2` / `.is-level-3`
       modifier classes with progressive `padding-left`
     - Vertical hairline connector on the left (same drafting-line
       visual the lo-fi drew)
     - ARIA: `role="treeitem"` `aria-level="2"` / `"3"`,
       `aria-expanded` if the row itself has children
     - Leaves get the normal Open button
   - Wrap the `<tbody>` in a container carrying `role="tree"` +
     `aria-labelledby` pointing at the group header.

5. **Disclosure interaction:**
   - Click on parent row OR on the disclosure triangle: toggle
     `state.expandedRows` for that publicId.
   - **Surgical DOM patch** (mirror R4-C-1b): only the affected parent
     + its immediate children are re-rendered. Focus stays on parent.
   - When a level-1 parent (repeater) is collapsed, its level-2
     children AND any expanded level-3 grandchildren all disappear
     from the DOM — but `state.expandedRows` remembers a
     grandchild's expansion so re-expanding the level-1 restores the
     nested state.

6. **Keyboard navigation** (Notion pattern, WCAG AA):
   - `ArrowDown` / `ArrowUp`: move focus between visible tree items
     (respecting the visible flattening of collapsed subtrees)
   - `ArrowRight`: on a collapsed parent → expand; on an expanded
     parent → focus first child; on a leaf → no-op
   - `ArrowLeft`: on an expanded parent → collapse; on a child with a
     parent → focus parent; on a top-level → no-op
   - `Home` / `End`: jump to first / last visible tree item
   - `Enter` / `Space`: on parent → toggle expand; on leaf → Open
   - Focus visible ring: reuse existing drawer focus styles

7. **Search auto-expand:**
   - When `state.q` is non-empty and a match reaches a leaf, populate
     `state.searchAutoExpanded` with all ancestor publicIds of every
     match — the render pass unions this with `state.expandedRows`
     when deciding what to show.
   - When search clears: `state.searchAutoExpanded` empties; the tree
     collapses back to the user's own `state.expandedRows` set.
   - The R4-C-1a server-side `q` param stays unchanged — server
     returns matching leaves + their parents (parents already flow
     from the flat list; children link back via `parentPublicId`).

8. **IntersectionObserver / value-summary batch:**
   - `registerVisibleValueSummaryTargets(wrap)` is called on the
     newly-appended children when a parent expands (mirrors R4-C-1b's
     existing pattern).
   - Parents are NEVER registered — they have no summary shape.
   - When a parent collapses, its children's IO registrations are
     released via the existing observer cleanup.

9. **CSS additions in
   [`control-center.css`](../../../addons/visual-editor/assets/css/control-center.css):**
   - `.__row.is-parent` / `.is-child` / `.is-grandchild`
   - `.__row-disclosure` — 14×14 triangle; rotates 90° on
     `[aria-expanded="true"]`; suppressed by `prefers-reduced-motion`
   - `.__row-childcount` — chip mirroring the R4-C-2 group-count style
   - `.__row.is-level-2 { padding-left: 32px; }`, `.is-level-3 {
     padding-left: 52px; }`
   - Vertical hairline connector: 1.5px `linear-gradient` on
     `background` positioned at the correct indent per level
     (avoids DOM-heavy pseudo-elements)

10. **[`AssetLoader.php`](../../../addons/visual-editor/src/Assets/AssetLoader.php)
    i18n additions** (~5-6 keys):
    - `controlCenterTreeExpand`, `controlCenterTreeCollapse`
    - `controlCenterTreeChildCountOne`, `controlCenterTreeChildCountMany`
    - `controlCenterTreeKeyboardHint`
    - `controlCenterTreeAncestorExpandedForSearch`

11. **Save-status-strip (R4-D-1) integration:**
    - Zero changes. Leaves fire `dbvc:visual-editor:panel:saved` with
      their own publicId as the token. The strip already gates on
      `token === state.activeToken`. Works uniformly for tree leaves.
    - Concurrent-reorder detection from the resolver surfaces as an
      error payload in the save response; the strip variant for that
      is an OPTIONAL polish in this slice — if the panel already
      surfaces resolver errors as inline banners, no strip change is
      needed.

## R5.7-c — Real-browser QA + release notes

### Goal

Close R5.7 by verifying the tree on the actual LocalWP site and
updating the release-notes + rollback runbook.

### Steps

1. **Real-browser QA at 1440×900 and 1280×720** (D-058 desktop-only).
   Checklist:
   - Toolbar → Brand Control Center → drawer opens
   - Repeater parent row renders with disclosure + count chip
   - Click parent → row children expand
   - Click a row → its subfield leaves expand
   - Focus continuity across expand / collapse
   - Keyboard nav: arrow keys, Enter, Home / End all work
   - Click Open on a leaf → editor panel opens with the correct
     subfield of the correct row
   - Edit + Save → save persists to the correct row (verify by
     opening a different row and confirming its subfield is
     unchanged)
   - Concurrent-reorder scenario: open a leaf in the drawer, reorder
     rows in a second ACF admin tab, try to save → `ConcurrentReorderDetected`
     surfaced as a specific error (no data loss)
   - Search: type a leaf-only term → ancestors auto-expand and match
     visible
   - Clear search → tree collapses back to viewer's prior state
   - Reduced-motion viewer (system preference or `data-theme`
     equivalent) → no rotation transition on disclosure
   - The 397 pre-existing available records unchanged
   - The existing Shared Globals popover unchanged (unrelated regression check)

## Cross-cutting design decisions (locked in advance)

### D-R57-01 · Server stays flat

The list endpoint returns records in a flat array with an optional
`parentPublicId` link. The client computes the tree structure at render
time. Rationale: keeps the R4-A backend contract stable across UI-shape
evolution; keeps `providerErrors` semantics simple (a provider fails
whole, not per-tree-branch); avoids a viewModelVersion bump beyond a
single-field addition.

### D-R57-02 · No R5.7-specific kill switch

The R3-D two-part kill switch (master Visual Editor + Enable Brand
Control Center) remains the authoritative gate. Adding a
`dbvc_visual_editor_control_center_tree_view_enabled` sub-switch would
fragment the test surface without buying real safety — the tree is a
first-class drawer concept, not a bolt-on feature. If the tree
introduces a live-site problem, the R3-D switches roll back the whole
drawer; R5.7-a's backend has its own rollback recipe that returns the
drawer to the pre-R5.7 flat-record state.

### D-R57-03 · `parentPublicId` is a registry primitive

Not a Vertical-specific hack. Future providers (Bricks portability
provider, cross-repo scoping providers, etc.) can emit tree
relationships through the same field. The safe list projection carries
it because a publicId is opaque to the client — treating it as
target-identifying would be wrong; treating it as opaque metadata is
correct.

### D-R57-04 · Descriptor row-signature is authoritative for stale detection

The `expected_row_signature` computed at descriptor-mint time and
re-verified at save time is the single source of truth for
concurrent-reorder detection. Row keys (if ACF exposes them) are
used as the primary lookup mechanism but do NOT replace the signature
— a row's identity might survive a reorder, but its contents might
have changed between mint and save. The signature catches both cases.

### D-R57-05 · Search stays server-`q` + client-auto-expand

The R4-C-1a server-side `q` filter returns matching leaves (and
parents flow through the flat list unchanged). The drawer computes
the ancestor set client-side and populates `state.searchAutoExpanded`.
Rationale: no server change needed; ancestor-set computation is
O(matches × depth) which is trivially small; and the two axes
(server filter + client auto-expand) can evolve independently.

### D-R57-06 · Expansion state is per-viewer, not per-drawer-session

`localStorage['dbvc.ve.control-center.expanded-rows']` persists across
sessions (mirrors the R4-C-2 group-expansion pattern). Records only
deviations from the "collapsed by default" rule so new fixtures still
default to collapsed as they're added.

### D-R57-07 · Parent rows have no Open button

A parent's role is disclosure, not editing. Clicking anywhere on the
parent row toggles its expansion. This preserves the "Open contract
means one leaf, one descriptor, one panel" invariant that every prior
R5.x slice has honored — no exceptions at parent level.

### D-R57-08 · Value-summary chips only on leaves

Parents render no chip. A "roll-up" summary at the parent
(e.g. `[3 rows · 8 posts total]`) is deliberately out of scope for
MVP — it forces the server to compute an aggregation shape that
doesn't map cleanly onto the per-family `build*Summary` static
builders, and the count chip already telegraphs "there are children
here." A future slice could add roll-up summaries as a separate
enhancement.

## Follow-up sub-slices (not in R5.7-C-1 scope)

### R5.7-C-2 · Drag reorder (optional, deferred)

Adds a drag handle to each level-2 (row) tree item. Drag reorders rows
within a repeater; commit fires a new REST endpoint
`POST .../repeater/reorder` with `{parent_field_key, new_order:
[row_index_or_key, ...]}`. Introduces a new mutation authority —
needs its own capability gate + audit path + save-status-strip
variant ("Row order saved"). Own kill switch
(`dbvc_visual_editor_control_center_row_reorder_enabled`) because
it's a behaviorally distinct capability from field editing.

### R5.7-C-3 · Roll-up parent summaries (optional polish)

Adds computed aggregate chips to parent rows: `[3 rows · 8 posts
total]` for a repeater whose subfields include a relationship, etc.
Needs a new provider hook `buildRepeaterRollupSummary($record)` and
new client renderer branches. Low priority — the count chip already
does the primary job.

### R5.7-C-4 · Expand-all / collapse-all controls

Adds a small header control (mirrors R4-C-2's view-toggle placement)
for global expand / collapse. Simple slice; deferred to gather usage
data first (viewers may not need it).
