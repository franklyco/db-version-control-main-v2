- Hotfix R5.later-y-2d — palette swatches were showing default black instead of the site's **current stored colors**. Root cause: `buildPaletteOverviewDescriptor` resolved each leaf's current hex via `get_field($leaf_field_key, 'option')` directly, which returns empty for Vertical's deeply group-nested palette colors (`brand_color_palette>vertical_global_palette>colorAccent`). ACF stores group subfields under prefixed meta keys (e.g. `options_brand_color_palette_vertical_global_palette_colorAccent`), and correctly reading them requires the group-write-path traversal that `AbstractAcfResolver::readGroupedFieldValue` performs — the same code path a single-color panel already exercises when it opens a palette leaf. Fix: for each leaf, mint the leaf's own full editable descriptor via the DBVC `SharedGlobalsDescriptorFactory` (which populates `source.group_write_path` for group-nested fields via `walkGroupChain`), then read the current value via `AcfColorPickerResolver::getValue($leaf_descriptor)`. This mirrors the single-color panel's currentValue read byte-identical — group-nesting + top-level fields both work correctly. Belt-and-braces fallback: if the resolver returns empty AND the ACF field carries a `default_value`, use that (matches the single-color panel's behaviour where the color input shows default_value when storage is empty). `try/catch` guards the factory build so any per-leaf failure only empties that one swatch rather than breaking the whole palette panel. `$pageContext` is now used (previously `unset()`) so it flows through to the leaf descriptor build.
